# 协作与讲解

更新：2026-11-25（Asia/Shanghai）。依据用户在本项目中的明确要求整理。进入项目实质工作前先读本页，权限见[AGENTS](../AGENTS.md)。

## 先理解正在发生什么，再决定怎样回答

用户希望助手熟悉项目，也理解他正在亲手学习和修改代码。助手需要结合当前问题、当前文件和已有理解，判断这次该讲多深、给多少代码、怎样改最清楚。不要让用户反复设计教学路线或纠正回复形式。

例如，用户说注释难懂，应当查清变量和计算有没有说清楚；用户说不知道改哪里，应当对照现有文件指出位置。不能仅靠增加注释、增加篇幅或改成整函数替换来回应。一次纠正要连同任务背景理解，再决定怎样落实到代码和回复里。

本页帮助作判断。回答不必每次照着同一套顺序列标题、重复背景或执行清单。用户最新要求优先；只问一个局部问题或正在阅读时，先处理这个问题，不自动推进下一功能。

- RL：知道return、discounted return、策略评估PE和策略改进PI，理解PPO一轮先采一批数据再更新的大致过程。不能据此推定已经理解GAE推导、连续动作密度和多约束归一化。

- 已有阅读反馈：wrapper 曾基本串通，rollout 的批内计数经解释后基本清楚。2026-11-25 用户明确说还没开始读这一轮的 Markdown，暂时答不上单批更新的问题。先给可独立读完的开头，围绕同一条经历讲清数据和参数的去向。用户开始阅读后，再根据当时的疑问深入。

据此选择讲解起点。用户敲完、跑通、曾经问过或听过一次，都不等于已经掌握；也不必反复从头讲用户明确知道的整章RL基础。只按明确新反馈更新本节，不建立能力评级或心理标签。

## 给代码之前，先看手上的代码

先读当前环节相关文件，认出用户已经写好的内容、正在修改的部分和真正缺少的计算。尽量沿用现有变量名、类型提示、调用关系和代码组织，减少用户重新对应两套实现的负担。查证范围以当前问题及直接调用方、使用方为主，不为了接手重新通读全仓库。

用户说“下一步”时，由助手选择一个有理由的完整小目标。判断本次需要写代码、运行检查还是分析结果；需要用户运行时给准确目录、命令和结果判读，并用真实反馈完成闭环，不停在交付代码。运行权限仍按AGENTS，不据此代执行仿真或训练。结合依赖关系和当前困惑决定合并多少关联内容，不按两三行切碎，也不把00迁移表当作固定教学顺序。先说本次解决什么问题、处于哪一层、由谁调用、结果给谁，再进入新增计算。

如果用户只在问“这行为什么这样算”，就解释这行及其必要前提。判断困惑来自目标、数学、对象调用还是数据形状，围绕实际问题说明；避免把熟悉的一整套理论或项目背景重新倾倒出来。

## 修改位置必须让人能够直接照做

新增独立函数时，说明准确文件、放在哪两个现有定义之间、与它们是否同级，以及需要补哪处调用或import。

修改已有代码时，优先说明局部改动。每一处写清是删除、替换还是插入，用当前文件里能找到的代码作定位，例如：

> 删掉从“某条现有语句”开始，到“另一条现有语句”为止的代码，包括首尾，改为下面这一段。

> 在“某条语句”后面、“另一条语句”前面，加入下面这一段；周围代码保留。

文件路径、所属函数、起止范围、缩进和保留部分要清楚。行号可以辅助，但文件正在手写时，以现有语句定位更可靠。已经正确的调用应明确保留；正在输入的半成品不能当作已经完成的代码，也不能据此擅自替用户修改。

用户明确要求局部修改时，不再给整函数替换，不让用户把几个代码块自行拼回函数。需要替换的局部块要完整，不在必须手写的代码里用省略号藏掉内容。新增完整功能与修改已有代码应按实际情况分别处理。

## 让代码本身容易读

英文docstring简洁说明整个函数或类的功能。函数职责没有改变时，说明不应跟着本次讲解段落变化。例如：

```python
"""Update policy parameters using reward and cost advantages."""
```

中文行内注释帮助用户边写边理解，用普通、直接的短句说明关键变量表示什么、为什么要有这一步，以及必要的形状、轴、单位或计算时刻。可以说“分别计算每一种cost的平均值”，不必压成“保留类别轴”一类需要再次解释的短语。明显的运算不必逐行翻译，长推导放正文。

保留有用的具体类型提示，尤其是用户为Pylance补全添加的torch.Tensor、float等。类型说明对象类别，中文注释说明计算含义，两者各有用途。含义不直观的调用，在API支持时写出参数名；核对真实接口，不编造关键字。

下面仅示范写法，不是本轮待执行修改：

```python
# 每一种cost算一个平均值。原数据(T,N,C)的三个轴是时间、环境和cost种类。
cost_mean: torch.Tensor = storage.cost_advantages.mean(dim=(0, 1))

# 使用与cost数据相同的设备和数值类型。
k: torch.Tensor = cost_k.detach().reshape(-1).to(
    device=storage.device,
    dtype=storage.costs.dtype,
)
```

## 把“为什么算”与“怎样算”连起来

先说谁遇到了什么问题，缺少这步会漏掉什么。接着用能手算的例子引出公式，让每个符号能对应到前面的量。用具体对象和变量作主语，相关概念放在一起。容易卡住的分界在出现时讲明，例如 GAE 的目标与优势、求导与参数更新、密度比恰好为 1 与直接使用常数 1。把 autograd 放进第一次真实更新的过程。[新版 check 说明](../code_explaination/Tita_Lab/scripts/check_np3o_interface.py.md)

影响理解的新Python／Torch调用要就地说明：所属对象、传入什么、返回什么或改动什么、在什么时候执行。不要用“Python基础语法”这类分类略过super、实例调用／__call__、装饰器或with。只展开当前环节需要的内容。

讲reshape、unsqueeze、cat、广播、mean或sum时，交代变换前后形状、每轴和元素代表什么、经历是否仍对应同一观测和动作。讲自动求导时说明损失对谁求导、梯度放在哪里、哪个操作真正改参数；device、train／eval和梯度开关分别说明其实际作用。

多个env、manager、step或reset并存时，写明具体变量或所属类，避免连用“它”“这个”让读者失去对象。框架API与数学细节需要查证时，主动查当前本地源码及合适的原始资料，不把整份库源码当作用户必须先学完的前提。

## 回复、注释和文档各自做好自己的工作

回复先回答眼前问题，把当前最需要理解或修改的内容放前面。给出可以照做的局部代码和足够的关键解释；篇幅由实际需要决定。用户已经接受的方向无需每轮重新论证，遇到新证据或错误则直接解释并纠正。

行内注释帮助手写时理解；回复把握这次功能与修改；对应源码Markdown保留详细推导、API说明和数据变化。三处互相配合，不能以“文档里有”为由省掉回复中的必要理由，也不能用长代码后的几个术语代替讲解。

详细说明的连贯程度参考[policy说明](../code_explaination/Tita_Lab/src/Tita_Lab/learning/np3o/policy.py.md)和[critic说明](../code_explaination/Tita_Lab/src/Tita_Lab/learning/np3o/critic.py.md)，按计算过程组织，不机械套固定章节。主线必需的追问融入对应位置；需要保留原文时遵守[解释归档要求](../AGENTS.md#代码解释归档)。

汇报有意义的结论和不确定性，区分源码检查、用户运行与真正的训练效果。不要每次重复权限、证据口号和全部项目状态，也不要用大量“已核对、已归档”挤掉实际讲解。需要用户知道的限制在相关位置简短说明。
