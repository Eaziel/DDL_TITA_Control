## 1. Gym的六个数是什么

| 内容 | 列数 | 计算 |
| --- | --- | --- |
| 机身坐标系线速度 | 3 | [vx,vy,vz]×2 |
| 左右轮接触判断 | 2 | OR滤波后的布尔值转float，再减0.5 |
| 动作历史选择编号 | 1 | 编号/(L-1)，当前L=3 |

每策略步先从接触力得到contact=(Fz>1 N)，再算filtered=当前原始contact OR 上一策略步原始contact。原始[True,False,False]会输出[True,True,False]，填补一次短暂丢失；真离地也可能晚一次采样才显示无接触。它不改物理接触或受力。

延迟编号0/1/2编码为0/0.5/1，对应的实际延迟是5/2.5/0 ms。L=1时分母取1，编号0输出0。

旧Gym先取得速度与接触，再执行回调推扰和环境reset，最终观测继续使用先前取得的值。迁移需要同时保留计算公式和取数时机。

## 2. Lab怎样保存本策略步的数据

TitaPrivilegedState对象保存以下成员：

| 变量 | 含义 |
| --- | --- |
| _linear_velocity | 本策略步取得的机身系速度，(N,3) |
| _last_contacts | 上一策略步的原始接触判断，(N,2) |
| _filtered_contacts | 当前OR后的输出，(N,2) |
| _sample_step | 最近已完成采样的全局策略步号 |
| _lag_denominator | 归一化分母max(L-1,1)，避免L=1时零除 |

common_step_counter每策略步加1，当前每10 ms一次。同一步多次调用时，只更新一次速度和接触：

```python
    def __call__(
        self,
        env: TitaVelocityEnv,
        asset_cfg: SceneEntityCfg,
        sensor_cfg: SceneEntityCfg,
    ) -> torch.Tensor:
        """Return six privileged features with one contact update per policy step."""

        if self._sample_step != env.common_step_counter:
            forces_z = self._sensor.data.net_normal_forces_w.torch[:, sensor_cfg.body_ids, 2]
            contact = forces_z > 1.0

            # 当前原始判断OR上一次原始判断，两次采样间隔10 ms。

            self._filtered_contacts.copy_(contact | self._last_contacts)
            self._last_contacts.copy_(contact)
            self._linear_velocity.copy_(self._robot.data.root_lin_vel_b.torch)
            self._sample_step = env.common_step_counter

        # 将目标位置编号0/1/2编码为0/0.5/1，得到(N,1)。
        lag_slot = env.action_lag_indices.to(dtype=torch.float32).unsqueeze(1) / self._lag_denominator

        return torch.cat(
            (
                2.0 * self._linear_velocity,
                self._filtered_contacts.float() - 0.5,
                lag_slot,
            ),
            dim=-1,
        )
```

第一次进入新策略步时更新成员并记下步号；之后同一步读取直接拼接已保存的成员。完整初始化与变量问答见[observations.py解释](../../code_explaination/Tita_Lab/src/Tita_Lab/tasks/velocity/mdp/observations.py.md)。

## 4. 为什么在reset前和push前各调用一次

| 本策略步发生什么 | 首次取数位置 |
| --- | --- |
| 没有reset、没有push | 最终ObservationManager计算观测时 |
| reset | 环境_reset_idx进入父方法之前 |
| push，且尚未取数 | 推扰函数改写速度之前 |
| 同一步先后触发多个位置 | 第一个位置保存，后续复用同一步数据 |

环境的_reset_idx先取数，再让父方法清传感器和改机器人状态：

```python
# 保存本步速度与接触，再重置场景、事件和管理器。
self.observation_manager.compute_group("privileged_state")
super()._reset_idx(env_ids)
self.proprio_history.reset(env_ids)
```

推扰函数也在写速度前调用：

```python
# 保存本步速度与接触，再覆盖水平速度。
env.observation_manager.compute_group("privileged_state")
```

例如物理结束速度为0.8 m/s，推扰把它改为-0.3 m/s，提前调用已把0.8复制到类成员。最终读取时步号未变，仍返回0.8×2。调用的返回值即使没有变量接收，成员更新也已经发生。

这个组没有噪声和原生历史项；两处调用不重算其他组，也不推进仿真。类沿用空reset保留本步数据和接触记忆，对应旧自动reset行为。首次step前仍是零速度/无接触初值；旧公开reset多一个零动作step的差异保留。

## 5. 五个组怎样拼成586列

环境返回按名称组织的obs字典。observation_layout.py定义明确顺序，从字典取得五个整组张量，检查后横向拼接：

```python
def pack_tita_observations(
    observations: Mapping[str, torch.Tensor],
) -> torch.Tensor:
    """Assemble the task's 586-feature training input with final clipping."""

    # 每段依次指定观测组名称和列数。
    layout = (
        ("policy", 33),
        ("scan", 187),
        ("privileged_state", 6),
        ("dynamics", 30),
        ("history", 330),
    )

    # 暂存各组的完整张量，循环结束后拼接。
    blocks = []
    for name, size in layout:
        # name取字典中的键；size指定本组应有的列数。
        value = observations[name]
        if value.ndim != 2 or value.shape[1] != size:
            raise ValueError(f"Expected '{name}' with shape (N, {size}), got {tuple(value.shape)}.")
        blocks.append(value)

    # 只裁剪新拼出的输出，内部观测/历史保留原值。
    return torch.cat(blocks, dim=-1).clamp(-100, 100)
```

| 输出列（右端不含） | 组 | 列数 |
| --- | --- | --- |
| 0:33 | policy | 33 |
| 33:220 | scan | 187 |
| 220:226 | privileged_state | 6 |
| 226:256 | dynamics | 30 |
| 256:586 | history | 330 |

6+30在这里构成旧输入中的36列区段。cat生成新输出，末端clamp不改变内部policy/history。当前TitaNP3OEnvWrapper在reset/step后调用本函数，自有check已消费586列；random_agent与普通PPO模板仍直接使用各自约定的观测组。586不是第六个观测组。

layout循环、元组解包和append的逐轮例子见[布局函数解释](../../code_explaination/Tita_Lab/src/Tita_Lab/tasks/velocity/observation_layout.py.md)。

## 补充问答

**Q：** 我没理解你说的：依赖顺序仍然是：动作延迟 → 上条的地形/动力学参数 → 本条。

**A：** 这是建议开发顺序，之前表达为严格依赖不准确。六维项读取动作的选择编号和历史长度，扫描与动力学参数各自独立；最终586拼接才需要五组都存在。

**Q：** 我没动接触为啥要或滤波？有什么意义吗？

**A：** OR用于处理Fz>1 N得到的布尔判断，不改变物理接触。原始True、False、False会输出True、True、False，可填补一次短暂丢失。真离地也会多保留一次采样，因此是遵循旧Gym计算约定，不保证判断更加真实。两次原始样本相隔10 ms；不能改成与上一滤波结果OR。

**Q：** 我没懂两处self.observation_manager.compute_group("privileged_state")在干啥。

**A：** 两处分别在机器人reset前和推扰改速度前，要求观测对象立刻把速度/接触保存到自身成员变量。即使没有接收返回值，保存动作也已发生。最终统一计算观测时，_sample_step发现还是同一步，继续返回保存的内容。普通步没有提前调用，就在最终计算观测时首次取数。此行为由自定义类实现，compute_group不会自动为所有观测冻结数值。逐行及具体速度示例归档于对应源码解释。
