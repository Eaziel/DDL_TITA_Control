# 13 训练观测：地形高度与机器人随机参数

**目标与结果：** 把地面高度和实际随机参数分别整理成187列、30列，供后续训练按需读取。

整理：2026-10-26。scan187与dynamics30已写，当前CPU公式和配置检查通过。当前wrapper已调用586拼接函数；完整训练循环尚未消费。 当前证据与整体状态以[项目记忆](../../PROJECT_MEMORY.md)为准。

## 1. Gym原来提供什么

旧compute_observations把当前33列、高度187列、额外36列和历史330列拼成586列。36列里，六列是速度/接触/延迟编号，另30列是本章的随机参数。

这些列是否进入动作网络，要看训练网络的切片。旧ActorCriticBarlowTwins的动作分支读取当前帧和历史；奖励/cost价值分支还使用高度与额外参数。环境提供数据，训练代码决定怎样消费。

## 2. 187个高度怎样算

Gym先取得机身附近17×11个地面高度，再计算：

$$
h_{n,k}=5\operatorname{clip}(z_{base,n}-0.4-z_{ground,n,k},-1,1),\qquad k=1,\ldots,187.
$$

$n$ 表示环境，$k$ 表示扫描点。输入高度单位为m；输出已经裁剪、缩放，不能直接当作未经处理的高度读数。

0.4 m是参考机身离地高度。平地上机身z=0.4时输出0；机身z=0.5时输出0.5。每个采样点各算一次，共187列。

Lab场景已有height_scanner，用射线与地形交点提供z_ground。当前PhysX实现中，20 m配置偏移只抬高射线起点，sensor.data.pos_w仍是绑定机身的位置，所以观测公式不再减20。

```python
@configclass
class ScanCfg(ObsGroup):  # 单环境187维。
    """Terrain heights relative to the nominal base clearance."""

    heights = ObsTerm(
        func=mdp.height_scan,
        params={"sensor_cfg": SceneEntityCfg("height_scanner"), "offset": 0.4},
        clip=(-1.0, 1.0),
        scale=5.0,
    )

    def __post_init__(self) -> None:
        self.enable_corruption = False
        self.concatenate_terms = True
```

height_scan提供z_base-0.4-z_ground，ObservationManager再clip后scale，恰好对应上述公式。扫描网格及点序见[02 Scene](02_scene迁移.md)。

## 3. 30列随机参数怎样算

| 内容 | 列数 | 保存/读取的值 |
| --- | --- | --- |
| 基座质量变化 | 1 | 当前质量减名义质量，kg |
| 基座质心变化 | 3 | 当前局部COM减名义COM，m |
| 摩擦系数 | 1 | 材质事件实际选中的系数 |
| 恢复系数 | 1 | 材质事件实际选中的系数 |
| 电机强度因子 | 8 | 八关节实际采用的倍数 |
| Kp因子 | 8 | 八关节实际采用的倍数 |
| Kd因子 | 8 | 八关节实际采用的倍数 |

TitaDynamicsParameters负责取数，没有在这里再次随机化。随机数仍由已有Event产生，之后既影响机器人，也能由观测读取。

### 先保存名义值，后读取实际变化

ObservationManager先构造观测类，之后才执行startup。因此类初始化时clone质量和COM作为基准，正常读取时作差：

```python
# startup之前保存名义基准，避免随资产数据更新而改变。
self._nominal_mass = self._asset.data.body_mass.torch[:, self._base_id].clone()
self._nominal_com = self._asset.data.body_com_pos_b.torch[:, self._base_id].clone()

# 以下为__call__中的计算：当前值减去已保存的基准。
delta_mass = self._asset.data.body_mass.torch[:, self._base_id] - self._nominal_mass
delta_com = self._asset.data.body_com_pos_b.torch[:, self._base_id] - self._nominal_com
```

例如名义质量13.2 kg，startup变为14.0 kg，这一列就是0.8。类默认reset不清基准，适用于当前startup抽一次、跨回合保留的随机化方式。

### 材质与电机因子取自既有对象

材质事件构造时已经选好每台机器人的系数；观测类取得该事件实例，把(N,)系数转换到环境device并扩成(N,1)。

每个执行器只持有自己负责关节的因子。观测先按actuator.joint_indices放回机器人关节列，再按asset_cfg.joint_ids取出任务指定的八列。这样无论底层关节怎样排序，输出始终遵循TITA_JOINT_NAMES。

```python
# factors按顺序存三个(N,8)张量：强度、Kp因子、Kd因子。
# 质量差增加列轴后为(N,1)，所有项按列拼接，得到(N,30)。
return torch.cat(
    (delta_mass.unsqueeze(1), delta_com, self._friction, self._restitution, *factors),
    dim=-1,
)
```

完整类与cat、device问答见[observations.py解释](../../code_explaination/Tita_Lab/src/Tita_Lab/tasks/velocity/mdp/observations.py.md)。此处为计算节选，delta_mass对应当前源码的delta_mess变量。

## 4. .pyi导出，再放进cfg

mdp/__init__.pyi的__all__增加TitaDynamicsParameters，并并入.observations导入：

```python
from .observations import TitaDynamicsParameters
```

height_scan已由官方MDP转发，无需另写同功能函数。随后在ObservationsCfg中选择自定义参数类：

```python
@configclass
class DynamicsCfg(ObsGroup):  # 单环境30维。
    """Randomized physical parameters available during training."""

    parameters = ObsTerm(
        func=mdp.TitaDynamicsParameters,
        params={"asset_cfg": SceneEntityCfg(
            "robot", body_names="base_link",
            joint_names=TITA_JOINT_NAMES, preserve_order=True,
        )},
    )

    def __post_init__(self) -> None:
        self.enable_corruption = False
        self.concatenate_terms = True

# 以下两个字段放在ObservationsCfg中，成为返回字典的键。
scan: ScanCfg = ScanCfg()
dynamics: DynamicsCfg = DynamicsCfg()
```

配置说明取哪个机器人/身体/关节及调用哪个类；ObservationManager负责建立实例和求值，不需要环境再手动创建这个类。

## 5. 为什么这样迁移，验证到哪里

场景只负责产生射线数据；官方height_scan完成标准高度计算；任务观测类负责把本项目随机参数排成约定的列。这样采样、随机化和训练输入的职责都能找到具体所属对象。

[当前代码CPU检查](../audits/2026-10-21_current_observations/dynamics_result.json)确认187点顺序、高度clip后scale、名义值捕获、材质值和三组因子重排、重复读取/部分reset通过。射线变换使用真实CPU Warp核，命中值与属性setter有替身，未验证真实地形边缘采样。

旧Gym查询高度表并取邻格最小值；RayCaster测量实际网格交点。公式与shape对应不代表两种物理输入完全相同。剩余六列及586布局见[14](14_特权状态与观测布局.md)。
