# 从论文复现到研究问题：测试与解释流程

日期：2026-11-13。按用户要求，删除原文件中助手拟定的研究题目、方法路线、优先方向及对应章节方案。当前工作方式为：选一篇可复现论文，建立对方法的理解，通过测试追查现象，再决定是否形成研究问题。

论文和仓库清单见[03](03_论文复现清单与仓库核查.md)。本篇是后续可以据具体源码执行的实验组织方式；没有运行其中的仿真、训练或板端实验，也不要求一次完成全部测试。

## 1. 一次只把一篇做成可解释的实验对象

开始时记录三件事：论文主要解决什么问题、关键机制是什么、哪项实验最能支持该机制。选择一条主张作为第一轮复现目标，不从全部论文图表或最大规模训练开始。

实际复现有不同层次：

| 阶段 | 本次结果能支持什么 | 需要留下什么 |
| --- | --- | --- |
| 已有权重回放 | 该权重在选定环境中的行为 | 权重来源、匹配配置、观测/动作接口、视频与时序 |
| 从头训练 | 所选实现与条件下能够学出对应行为 | 完整配置、训练曲线、随机种子、训练预算与模型选择依据 |
| 论文关键结果核对 | 所选机制与对照在该设置下的效果 | 原文实验与本地设置差异、基线、指标及重复结果 |
| 主动测试 | 该模型在某些新增条件下的响应 | 改变的条件、其余固定项、异常记录和可重复性 |
| 原因分析与方法实验 | 某种解释能否通过干预得到支持 | 竞争解释、可证伪预测、简单替代与负结果 |

每次只报告实际完成的层次。社区移植可提供实现材料，但需要核对它保留和改变了哪些原文机制；将四足方法迁到TITA时，另外记录形态、任务和执行接口的变化。

## 2. 先建立实验清单与正常行为

每组结果至少绑定：论文/报告版本、代码来源与版本标识、机器人资产、仿真器及版本、任务、权重、配置覆盖、物理/控制周期、随机种子、并行环境数，以及从头训练或加载权重的区别。本项目的Git读取与操作由用户管理，所需版本标识可以由用户提供；助手不会自动读取本项目Git。

先做一项作者正常条件下的代表性行为，确认单位、坐标、关节顺序、动作裁剪/缩放、历史更新、归一化、终止和重置。对有历史状态的模型，还要检查跨回合是否正确清理缓存。

若正常行为不能重复，先保留环境/API、配置、训练和资产错误等解释，暂缓讨论方法局限。无需把所有工程故障都扩展成论文问题。

## 3. 探索与受控测试交替进行

交互“玩模型”有助于发现现象。发现有意思的行为后，保存初始状态、指令与随机条件，使它能按脚本重放；随后每次主要改变一个因素。

下表是测试因素库，按论文主张选择少量项目。它不指定研究任务，也不要求同时增加所有传感器或故障模型。

| 因素 | 可以怎样改变 | 主要观察什么 |
| --- | --- | --- |
| 任务指令 | 原文范围内的恒定、平滑变化与分段变化 | 跟踪、超调、切换响应、实际执行需求 |
| 初始状态 | 原文允许范围内改变姿态、速度或构型 | 结果是否依赖单一起点 |
| 可用观测 | 原设置、受控噪声、缺失或延迟；分别处理 | 状态/表示变化是否解释控制响应 |
| 模型与执行 | 在合理范围内改变质量、驱动限制或响应 | 饱和、误差、恢复过程及物理可行性 |
| 环境 | 按原任务改变几何、接触或障碍条件 | 成功范围、失败过程、模型敏感性 |
| 计算预算 | 固定其他条件改变预测/采样预算或更新周期 | 性能、实际耗时、动作或规划的时效 |

先区分训练分布内测试和分布外测试。针对单因素得到解释后，再做少量有理由的组合；避免同时加入多个极端条件，得到一个无法归因的失败。

任务难度应有物理依据。超过力矩、几何或接触能力的任务可以用于确定边界，不能仅据这种失败指控算法存在可改进缺陷。

## 4. 需要怎样的记录，才能一路追查

按具体方法选取数据，保留原始时序而非只有平均reward：

- 时间、环境编号、回合与随机种子，指令、观测及其时间戳。
- 估计状态、历史或关键隐变量；与评价真值分别存放。
- 策略原始输出、裁剪/缩放后的目标及实际执行量。
- 关键物理量、约束违反、饱和、接触或碰撞、终止原因。
- 任务指标、各主要奖励/cost及模型预测误差；只存与当前主张有关的分项。
- 计算耗时与训练进度；有异步结构时另存数据年龄和动作保持。

一个异常记录包含：现象、首次出现时刻、出现前后的关键变量、最小重放条件、两三个竞争解释，以及下一项能够区分解释的实验。

例如，机器人响应变慢，候选解释可以包括输入时效、动作滤波、输出饱和或策略行为。先通过检查和受控干预区分这些原因，再讨论是否需要新结构。这个例子只说明诊断方式，没有预设研究问题。

## 5. 怎样设计有信息量的对照

**HIM实践示例：** 先追踪历史输入、速度估计、隐式表示和动作之间的关系。若要移除一个表示检验其必要性，应按原文设计训练相应消融，或明确称为推理时扰动测试。把已经训练好的输入随意置零，会引入新的分布变化，不能直接据此认定该模块没有价值。[HIM原文](https://arxiv.org/html/2312.11460)

**CaT实践示例：** 同时记录原始约束、终止概率、实际发生的环境reset和GAE/回报处理。该实现的概率表示未来奖励终止，不要求每次概率为正都物理重置；与奖励惩罚、硬终止或其他约束算法比较时，先对齐这些含义。[CaT原文§III-B](https://arxiv.org/html/2403.18765)

**DIAL-MPC实践示例：** 比较搜索机制时固定任务、输入信息和合理计算预算；分别报告同步等待与异步执行。优化更充分和允许更多计算都可能改善结果，需要区分它们。其算法核心和例程见[作者仓库](https://github.com/LeCAR-Lab/dial-mpc)。

不同论文的独立演示用于理解各自机制；要比较算法优劣，需要统一任务和信息条件。原任务上的复现与TITA适配也分别记录。

## 6. 发现现象后，怎样判断是否值得形成研究问题

先判断它能否重复，再判断其影响和原因。需要澄清：

1. 它影响了哪项有意义的任务、性能、数据、信息需求或计算代价？
2. 它来自实现、参数、物理不可行，还是现有方法的假设/机制？
3. 一个合理的强基线或简单设置能否解决？
4. 换初始状态、随机种子或相近任务后，这个现象是否仍有代表性？
5. 某个解释能否预测干预后的变化，并接受反例？

得到较可靠解释后，再定向检索相邻工作。借鉴另一篇论文时，写出它处理的困难、假设、输入和机制，说明这些条件在当前问题中是否成立。先做最小方法实验，检查收益是否来自关键机制，还是额外信息、更多预算或不同训练设置。

价值与新颖性分别论证。问题可以重要但已有充分解法；方法也可能形式新颖但收益很小。实验报告负结果同样有助于取舍，但一次调试失败或简单模块组合尚不足以构成完整研究贡献。

## 7. Orin与CAN安排在对应主张出现之后

已有Orin Nano 8GB可以用于完整推理链、数值一致性、处理器在环和时间测量。先明确板端要运行什么，再决定是否需要导出、优化和通信接口。

典型闭环为：电脑模拟机器人与传感器，Orin处理观测、维护历史并计算动作，电脑执行动作并返回反馈。同步等待模式适合功能核对；评价真实时间影响时，要保留迟到、丢包、动作保持及主机超时的作用。主机不能达到实时节拍时，可分别记录板端时序与延迟重放仿真，不声称硬实时验证。[在环实验术语](https://www.mathworks.com/discovery/hardware-in-the-loop-hil.html)

CAN编码/虚拟回环、真实总线收发、总线参与控制闭环是不同的验证层次。TITA实际协议、用户载板及外接收发器尚未核验；发送自定义报文不能证明实体TITA兼容。具体硬件依据需查实际版本的[NVIDIA CAN文档](https://docs.nvidia.com/jetson/archives/r36.4.4/DeveloperGuide/HR/ControllerAreaNetworkCan.html)。

这些验证回答计算与接口问题，不能测出缺席的真实执行器和轮地接触。无需把Orin/CAN设置成每篇复现的必做项目。

## 8. 现在怎样推进

先按03选HIM作为深入复现对象，或者在原Isaac Gym环境可用时先操作Walk These Ways的现成权重。正式执行前核对选定版本和本地资源，不在现有Lab环境中直接混装旧依赖。

助手可以继续完成一篇论文的源码调用链、原文关键实验到脚本的映射、记录字段与受控测试设计；用户通过原文阅读、代码与运行结果建立自己的判断。无需等全部迁移完成才能阅读或设计实验；实际运行和源码写入仍按项目边界进行。

每完成一轮，只保留有用的产物：可重复行为、主要现象、原因证据、未解释部分及下一项区分性实验。研究方向根据这些证据逐步形成。
